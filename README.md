# CookieSync

CookieSync — это инструмент для совместного и многократного использования одних и тех же cookies между разными браузерными сессиями. Он обеспечивает устойчивость, повторное использование и минимизирует повторные входы в систему используя общее разделенное хранилище.

### Разделенное хранилище

Каждый аккаунт хранится в отдельном JSON-файле в `cookieserver/accounts/`.
Расширение отправляет имя аккаунта в команде `register` сразу после открытия
WebSocket. Если аккаунта ещё нет, сервер создаёт и сохраняет его автоматически;
если он существует, клиент получает его текущие cookies. Сохранённые аккаунты
загружаются после перезапуска сервера.

Для общей синхронизации укажите одинаковое имя аккаунта во всех расширениях.
Новые имена: 1–64 буквы, цифры, `_` или `-` (до 200 байт UTF-8), кроме имён
устройств Windows (`CON`, `NUL`, `COM1` и т. п.). Существующие имена сохраняются.
Команды ручного создания и удаления удалены; список доступен через
`python -m cookieserver.manage list_accounts`.

### Возможности:
1. Обеспечивает автоматическое получение кук с сервера и отправку новых в совместное хранилище.
2. Автоматически создаёт аккаунты (разделённые хранилища) при регистрации клиентов.
3. Не детектируется серверами.
4. Поддерживает практически неограниченное количество подключений к одному аккаунту.

Поддерживаемые браузеры: Firefox, Edge, Chrome

### Установка и запуск сервера

**Windows:** [пошаговая инструкция](cookieserver/WINDOWS.md) — установка Python,
настройка аккаунтов, firewall, TLS и автозапуск через Планировщик заданий.
Готовый шаблон: [server_config.windows.conf.example](cookieserver/server_config.windows.conf.example).

Зависимости сервера находятся в `cookieserver/requirements.txt`.
Команды выполняются из корня проекта с установленными зависимостями:

```bash
python -m pip install -r cookieserver/requirements.txt
python -m cookieserver.manage --help
python -m cookieserver.manage runserver
```

Сервер читает `cookieserver/server_config.conf`. По умолчанию включён TLS:
нужны PEM-сертификат и ключ. Для проверки в доверенной локальной сети
используйте `python -m cookieserver.manage runserver --no-tls` и URL `ws://`.

### Сборка расширения для передачи пользователю

Из корня проекта (Python 3 и Node.js):

```bash
node --test
python3 build_extension.py
```

Также можно выполнить `make build-extension`. Версия берётся из
`extension/manifest.json`. Архивы создаются в `build/`:

- `CookieSync-<версия>-chromium.zip` — для Chrome, Chromium и Edge;
- `CookieSync-<версия>-firefox.zip` — неподписанная сборка Firefox для временной установки.

В каждом архиве есть `INSTALL_RU.txt` с инструкцией для пользователя.
Для Chrome/Edge нужно распаковать архив и выбрать «Загрузить распакованное»
на странице расширений в режиме разработчика. Постоянная установка в обычный
Firefox требует подписи Mozilla. Вместе с архивом передайте пользователю адрес
сервера и имя аккаунта. Подробности: [инструкция установки](extension/INSTALL_RU.txt).

Начиная с версии расширения 1.0.1 в манифесте явно задана CSP без
`upgrade-insecure-requests`: Firefox сохраняет выбранный пользователем протокол
`ws://` или `wss://`. Без этой настройки стандартная политика Firefox Manifest V3
автоматически переводит незащищённые соединения на TLS.

С версии 1.0.2 при регистрации в пустом аккаунте расширение отправляет уже
существующую локальную пару `ASP.NET_SessionId` / `ResoOffice60`, если открытая
вкладка `office.reso.ru` подтверждает вход. Для вкладок, открытых до установки,
проверочный скрипт подключается через `browser.scripting` (нужно разрешение
`scripting` и доступ к сайту). Если аккаунт уже содержит cookies, при подключении
применяется серверная пара. Причина блокировки первоначальной отправки показывается
в статусе расширения; открытие/перезагрузка вкладки повторяет начальную проверку.
